# Joshua-Client Build and Deployment

## Purpose and scope

Joshua-Client is the C++17 on-target client/test application. Its CMake project also adds the sibling `Joshua-HAL` tree, generates C++ protobuf/gRPC sources from `../Joshua-HAL/protos`, and emits executables under the CMake build `bin/` directory. This guide covers the repository-root Makefile workflow.

## 1. Prerequisites

- GNU Make, CMake 3.16 or newer, Ninja, a C++17 compiler, and `nproc`.
- `Threads`, `spdlog`, `tomlplusplus`, `yaml-cpp`, SQLite3, Protobuf, `protoc`, and `grpc_cpp_plugin` discoverable by CMake. The CMake configuration can use gRPC CMake packages or the `pkg-config` fallback.
- The sibling `Joshua-HAL` checkout must be present beside this repository because both CMake and generated-protocol inputs reference it.
- For cross builds: Docker with ARM64/QEMU support. `make docker-install` may install Docker through `sudo apt` if absent.
- For remote deployment: `sshpass`, SSH/SCP access to the target, and credentials. The defaults are user `nvidia`, password `nvidia`, targets `192.168.1.3` and `192.168.1.13`; override Make variables rather than committing credentials.

## 2. Setup

Run commands from this repository root. Native setup is performed by `make configure`; it creates `build/native` and runs CMake with Ninja and `-DBUILD_TESTS=ON`. Cross setup is performed by `make docker-image` or the higher-level Docker targets; the image mounts the parent `Joshua/` directory so the HAL sibling is visible.

## 3. Build and compile

- `make configure` - configure the native CMake/Ninja tree.
- `make build` - configure if needed and compile with Ninja using `JOBS` (`make JOBS=4 build`).
- `make docker-configure` - configure the ARM64 Docker build.
- `make docker-build` - build the ARM64 tree through Docker/QEMU; this is also the default `all` workflow.
- `make docker-shell` - open the ARM64 development container.

Native outputs are in `build/native/bin` and `build/native/lib`; cross outputs are in `build/cross/bin` and `build/cross/lib`.

## 4. Test and lint

- `make test` - native build followed by CTest filtered to `serializer_tests` and `runner_tests`.
- `make docker-test` - build and run the cross CTest suite in the ARM64 container.
- `make format` - run the generated Ninja `format` target and format discovered CMake files with `cmake-format`.
- `make cppcheck` - run the generated Ninja `cppcheck` target.

Formatting and static analysis require the corresponding tools in the host or Docker image. `make run` runs test applications, not a replacement for automated tests.

## 5. Packaging and artifacts

The Makefile does not define a package target. The supported artifacts are the native or cross `bin/` executables and `lib/` libraries. Use `make list` to enumerate available applications after building. Doxygen output is generated by `make doc`, which runs Ninja target `doc_doxygen` and requires the configured documentation tooling.

## 6. Deployment, install, and run

- `make deploy-a` / `make deploy-b` - cross-build, then copy `build/cross/lib` and `build/cross/bin` to `/tmp/acu-test/` on the selected target.
- `make deploy` - deploy to both configured addresses.
- `make run-a [app] [args...]` / `make run-b [app] [args...]` - deploy and run a selected application remotely; with no app, run all remote binaries.
- `make run [app] [args...]` - run native binaries with `LD_LIBRARY_PATH=build/native/lib`.

Remote targets require reachable NVIDIA devices, valid SSH credentials, and a compatible ARM64 userspace. The Makefile uses `StrictHostKeyChecking=no` and clears `/tmp/acu-test` before copying, so use only on intended test devices. This is a manual hardware verification step.

## 7. Cleanup

- `make clean` removes all native and cross build directories.
- `make docker-clean` removes the cross build directory inside the Docker volume.
- `make setup-completion` appends this repository's completion script to `~/.bashrc`.

## 8. Hardware, cloud, and manual verification caveats

There is no cloud deployment target. Native tests can run without hardware; ARM64 execution, remote `deploy-*`, and `run-*` targets require a compatible device and network. Confirm the target IPs and credentials explicitly with `IP_A`, `IP_B`, `USER`, and `PASS` before running deployment. Validate the resulting binaries and HAL behavior on the physical target; successful compilation alone does not verify device interfaces.
